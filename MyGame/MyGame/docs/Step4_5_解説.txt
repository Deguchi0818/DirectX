========================================
ステップ4.5: 行列変換の安全化 (ToXM / FromXM)
解説
========================================


■ 結論から
--------------------------------------------------
見た目も動作も何も変わっていない。
変わったのは「壊れる可能性」だけ。

耐震補強のようなもの。工事の前後で家の見た目は変わらないが、
地震が来たときに倒れるかどうかが変わる。
そして次のステップ(unique_ptr化)が、その地震にあたる。


■ 何を変えたのか
--------------------------------------------------
■ 変更前
    DirectX::XMMATRIX world = *(DirectX::XMMATRIX*)&worldMat;

■ 変更後
    DirectX::XMMATRIX world = ToXM(worldMat);


■ なぜ危険だったのか
--------------------------------------------------
XMMATRIX は、CPUのSIMD命令
(1回の命令で4つの数値をまとめて計算する仕組み)で
扱うための型。

この命令を使うには、データが「16バイト区切りの位置」に
置かれている必要がある。

    メモリ上の位置
    0    16   32   48   64
    |----|----|----|----|
         ↑ここならOK
       ↑ここだとNG(クラッシュや誤動作)

一方 MyMatrix4x4 はただの float[4][4] で、その保証がない。

    *(XMMATRIX*)&worldMat

この書き方は「この場所を XMMATRIX として扱え」と
強制的に宣言するもの。16バイト区切りに乗っていなければ、
プログラムが落ちるか、計算結果がおかしくなる。

今まで動いていたのは、たまたま位置が揃っていたから。
規格上は未定義動作であり、いつ壊れてもおかしくなかった。


■ どう安全になったのか
--------------------------------------------------
MyMatrix4x4.h に追加した変換関数:

    inline DirectX::XMMATRIX ToXM(const MyMatrix4x4& mat)
    {
        return DirectX::XMLoadFloat4x4(
            reinterpret_cast<const DirectX::XMFLOAT4X4*>(mat.m));
    }

    inline MyMatrix4x4 FromXM(const DirectX::XMMATRIX& xm)
    {
        MyMatrix4x4 out;
        DirectX::XMStoreFloat4x4(
            reinterpret_cast<DirectX::XMFLOAT4X4*>(out.m), xm);
        return out;
    }

ポイント:
  ・XMFLOAT4X4 は XMMATRIX と違い、アライメント要求のない
    普通の float[4][4]。MyMatrix4x4 と中身が同じなので
    このキャストは安全。
  ・XMLoadFloat4x4 / XMStoreFloat4x4 が、位置を気にしない方法で
    読み書きして XMMATRIX との変換を行ってくれる。

「強制的に同じものとして扱う」のではなく、
「きちんと読み込んで変換する」という違い。


■ なぜこのタイミングでやったのか
--------------------------------------------------
次のステップ5で unique_ptr を導入すると、
オブジェクトがメモリ上のどこに置かれるかが変わる。

    今まで : std::vector<GameObject>
             → 連続した領域に並ぶ
    変更後 : std::vector<std::unique_ptr<GameObject>>
             → 1つずつ別々の場所に確保される

つまり「たまたま揃っていた」という前提が崩れる。

そこで壊れると、原因が unique_ptr 化にあるのか
行列のキャストにあるのか切り分けられなくなる。
先に安全にしておけば、この問題を候補から外せる。


■ 置き換えた箇所
--------------------------------------------------
  GameObject.h        Draw() 内の3箇所
                      (world / xmView / xmProj)
  BoneAttachment.cpp  Update() 内の2箇所
                      (owner / m_boneTransform への書き戻し)
  GameInstance.cpp    デバッグ描画の viewProj(任意・統一のため)

確認方法:
  プロジェクト全体を次の文字列で検索してヒット0件なら完了。
  (imguiフォルダは対象外)
      *(DirectX::XMMATRIX*)&
      *(MyMatrix4x4*)&


■ つまずいた点と原因
--------------------------------------------------
【問題】識別子 "ToXM" が定義されていません

【原因】ToXM / FromXM を MyMatrix4x4 クラスの「中」に
        書いてしまっていた。

  クラスの中に書くと MyMatrix4x4::ToXM(...) という
  メンバ関数になる。メンバ関数はオブジェクトに対して
  呼ぶものなので、

      ToXM(view)

  という書き方では見つからない。

【対処】クラスの閉じ括弧 }; の「後ろ」に移動する。

    class MyMatrix4x4
    {
        // ...メンバ...
    };                    ← クラスはここで終わり

    inline DirectX::XMMATRIX ToXM(...)   ← この位置に置く

  これでどこからでも呼べるグローバル関数になる。


【補足】エラー表示が「エラー(アクティブ)」の場合

  これはコンパイラではなく IntelliSense(エディタの解析機能)が
  出しているもの。ヘッダを編集した直後は解析結果が古いまま
  残ることがよくある。

  対処:
    1. まずビルド(Ctrl+Shift+B)を実行する
       → 成功すれば実際のコンパイルは通っている
    2. それでも消えなければ、Visual Studio を閉じ、
       ソリューションと同じ場所の .vs フォルダ(隠しフォルダ)を
       削除して開き直す

  「エラー(アクティブ)」ではなく単に「エラー」と出ているものが
  本物のコンパイルエラー。


■ MyMatrix4x4 は使わない方がいいのか(判断の記録)
--------------------------------------------------
問題だったのは MyMatrix4x4 を使うこと自体ではなく、
XMMATRIX との間を行き来するときのキャストだった。

検討した2案:

  A案: DirectXMath に一本化し、MyMatrix4x4 を廃止する
       → 商用エンジンに近い形。SIMDによる高速化も得られる
       → Transform / Camera / Collider / DebugRenderer など
         広範囲に影響し、別の大工事になる

  B案: MyMatrix4x4 をエンジンの標準型として維持し、
       変換だけ安全にする(今回採用)
       → 変更が小さい割に、未定義動作という一番まずい問題が消える
       → 自作行列クラスは自作エンジンとしての価値もある
       → A案は今のロードマップとは独立した別プロジェクトになる

採用理由: 小さい変更で最大の危険を除去できるため。
