========================================
Transform と「回転」の扱いについて
＋ ゲームエンジンとしてのオーソドックス性
========================================


■■ 第1部: 回転はどこで計算されているのか ■■


● 結論
--------------------------------------------------
回転は「計算式の中にすでに含まれている」。
不足しているのは取得用API(GetWorldRotation)だけであり、
計算上は何も欠けていない。


● コード解説: m_localMatrix が作られるまで
--------------------------------------------------

【1】度数法をラジアンに変換する係数

    const float toRadian = 3.14159265f / 180.0f;

  Transformは角度を「度(degree)」で保持しているが、
  sinf/cosf はラジアンを要求するため、ここで変換する。
  ユーザーが扱う単位(度)と、計算で使う単位(ラジアン)を
  分けるのは一般的な作り。


【2】スケール・回転・移動を個別の行列にする

    MyMatrix4x4 matS = CreateScale(scale.x, scale.y, scale.z);

    MyMatrix4x4 matRX = CreateRotationX(rotation.x * toRadian);
    MyMatrix4x4 matRY = CreateRotationY(rotation.y * toRadian);
    MyMatrix4x4 matRZ = CreateRotationZ(rotation.z * toRadian);

    MyMatrix4x4 matT = CreateTranslation(pos.x, pos.y, pos.z);

  回転はX軸・Y軸・Z軸まわりの3つに分かれて作られる。
  この時点ではまだバラバラの状態。


【3】3つの回転行列を1つに合成する

    MyMatrix4x4 matR = Multiply(matRZ, matRX);
    matR = Multiply(matR, matRY);

  Z → X → Y の順で掛け合わせている。
  この「順序」が回転の結果を決める。
  行列の掛け算は交換法則が成り立たない(A×B ≠ B×A)ため、
  順序を変えると別の姿勢になる点に注意。

  → この matR が「回転成分」そのもの。


【4】SRTの順でローカル行列を合成する

    m_localMatrix = Multiply(matS, matR);        ← S × R
    m_localMatrix = Multiply(m_localMatrix, matT); ← (S×R) × T

  結果として m_localMatrix = S × R × T となる。
  つまり m_localMatrix には
      スケール・回転・移動の3つすべてが入っている。

  行ベクトル規約では、掛ける順序が
  「先に適用したいものほど左」になる。
  S → R → T の順で適用したいので、この並びになる。


【5】親との合成

    if (m_parent != nullptr)
        m_worldMatrix = Multiply(m_localMatrix, m_parent->GetWorldMatrix());
    else
        m_worldMatrix = m_localMatrix;

  m_localMatrix が位置・回転・スケールをすべて含んでいるので、
  この1行だけで
      「親が回転すれば子も一緒に回る」
      「親が移動すれば子もついていく」
      「親が拡大すれば子も拡大する」
  がすべて同時に実現される。

  回転のために追加の処理は一切不要。
  これが行列を使う最大のメリット。


● なぜ GetWorldRotation() を作らなかったのか
--------------------------------------------------

理由A: 現状のコードが必要としていないため

  ワールド値を要求しているのは当たり判定まわりだけだが、
  そのAPIは回転を受け取る口すら持っていない。

    AABB   GetWorldAABB(const MyVector3& parentPos,
                        const MyVector3& parentScale) const;
    Sphere GetWorldSphere(const MyVector3& parentPos,
                          const MyVector3& parentScale) const;

  引数は位置とスケールのみ。
  つまり現状のコライダーは回転を無視している
  (= 回転する箱の当たり判定は正しく取れない)。
  渡す先が存在しないAPIを先に作る必要はない。


理由B: 行列からオイラー角を逆算するのは壊れやすいため

  ・位置は行列の第4行 m[3][0..2] にそのまま入っているので
    確実に取り出せる(GetWorldPosition が成立する理由)
  ・一方、回転行列からX/Y/Zの角度を逆算する処理には
    次の落とし穴がある:

      - 同じ姿勢を表す角度の組み合わせが複数存在するため、
        設定した値と違う値が返ることがある
      - ジンバルロックの姿勢で計算が破綻する
      - スケールが混ざっていると先に正規化が必要になる

  「一見動くが特定の角度で急におかしくなる」
  というバグの温床になるため、必要になるまで作らない。


● 回転が必要になったらどうするか
--------------------------------------------------
オイラー角で取り出すのではなく、
「行列(またはクォータニオン)のまま使う」のが正解。

必要になる代表的な場面:

  1. OBB(回転する箱の当たり判定) … ステップ7以降
     → GetWorldRotation() で角度を取るのではなく、
       GetWorldMatrix() の回転部分をそのまま使う

  2. ボーンへの武器装着 … ステップ4
     → 行列のまま親に掛ければ回転は自動で伝わる

  ※ 改修前の Weapon::FollowToBone() は
     XMMatrixDecompose で行列をバラして回転を取り出していた。
     まさに「一度分解する」やり方であり、
     回りくどいうえに誤差も出やすい。
     ステップ4でこれを解消するのが狙い。


■■ 第2部: この方針はオーソドックスか ■■


● 結論
--------------------------------------------------
骨格は完全にオーソドックス。
商用エンジンとほぼ同じ構造になっている。

ただし実装の細部で、商用エンジンとは違う選択をしている
箇所が2つある(後述)。どちらも現在の規模では妥当だが、
将来引っかかる可能性がある場所として認識しておくとよい。


● 商用エンジンと一致している点
--------------------------------------------------

【1】local値とworld行列を分けて持つ

  Unity          : Transform (position / localPosition)
  Unreal Engine  : USceneComponent (RelativeLocation / ComponentTransform)
  Godot          : Node3D (position / global_position)

  いずれも「ローカル値」と「ワールド値」を明確に分けている。
  今回の m_localPosition / m_worldMatrix はこれと同じ考え方。


【2】親ポインタによる階層(シーングラフ)

  親を1つ持ち、world = local × parentWorld で合成する構造は
  3Dエンジンの標準形。
  「同じ仕組みでタイヤもライトも武器も付けられる」という
  利点も、各エンジンが実際に享受しているもの。


【3】親を所有しない(参照のみ)

    Transform* m_parent = nullptr;   // 所有しない。参照のみ。

  親子関係は「所有権」とは別物として扱うのが定石。
  子が親を delete してしまう事故を防げる。


【4】描画・物理・その他がすべて同じTransformを見る

  これがステップ2以降で目指している状態であり、
  まさに商用エンジンがやっていること。
  改修前のように「描画時にだけ親子計算する」のは
  典型的なアンチパターンだった。


● 商用エンジンと違う選択をしている点
--------------------------------------------------

【差異1】回転をオイラー角(度)で保持している

  商用エンジンの内部表現は原則クォータニオン。
  Unityも表示上はオイラー角だが、内部は Quaternion。

  オイラー角のままだと将来こうなる:
    ・ジンバルロック(特定の姿勢で1軸の自由度が失われる)
    ・回転の補間(Slerp)が正しく行えない
      → アニメーションのブレンドやカメラの滑らかな追従で問題化
    ・回転の合成が順序依存で直感に反する

  【今は変えなくてよい理由】
    現状の用途(プレイヤーの向き＝Y軸回転のみ、
    静的オブジェクトの固定回転)では問題が表面化しない。
    Player.cpp も Y軸回転しか使っていない。

  【変えるべきタイミング】
    ・アニメーションのブレンドを実装するとき
    ・カメラや敵の「滑らかに振り向く」処理を入れるとき
    ・3軸すべてが自由に回るオブジェクトを扱うとき


【差異2】更新順序を手動で制御している

  今の設計では「親→子の順にUpdateMatrix()を呼ぶ」ことを
  呼び出し側(GameInstance)が保証する必要がある。

  商用エンジンは以下のいずれかで自動化している:
    ・親が子のリストを持ち、親から再帰的に更新する
    ・ダーティフラグを立て、GetWorldMatrix()が呼ばれた時に
      必要な分だけ再計算する(遅延評価)

  【今は変えなくてよい理由】
    階層が1段(プレイヤー → 剣)しかないため、
    手動制御で十分管理できる。
    自動化の仕組みは、それ自体がバグの原因にもなりうる。

  【変えるべきタイミング】
    ・階層が2段以上になったとき
      (例: プレイヤー → 手 → 武器 → エフェクト)
    ・オブジェクト数が増えて毎フレーム全更新が重くなったとき
      → このときダーティフラグ方式が有効になる


【差異3】コライダーが回転に対応していない

  これは設計の差というより「未実装」の領域。
  ロードマップのステップ7(OBB)で解消予定。


● 総評
--------------------------------------------------
「Transformで階層を持ち、描画から親子計算を追い出し、
 物理を分離する」という方針そのものは、
ゲームエンジンの王道。

差異として挙げた2点は、どちらも
「小さく作って、必要になったら差し替える」
という判断であり、学習目的の自作エンジンとしては
むしろ正しい進め方。

重要なのは、
  ・なぜ今それを選んでいるか
  ・どうなったら変えるべきか
を自覚しておくこと。上記に記録した内容がそれにあたる。
